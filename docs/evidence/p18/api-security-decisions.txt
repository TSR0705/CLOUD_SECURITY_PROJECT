1. ROUTE SPECIFICATION & SECURITY CONTROLS
--------------------------------------------------------------------------------
Endpoints Implemented in services/api (services/api/src/routes/security-decisions.ts):
  - GET /api/v1/security-decisions/:id (and /security-decisions/:id)
    - Authentication:
      - API Key: Scoped and tenant-isolated to application_id. Cross-tenant access
        fails with HTTP 403 Forbidden.
      - User JWT: Allowed for admin, analyst, and auditor roles.
    - Response:
      - HTTP 200 with sanitized explainable decision record (sug.decision/v1),
        bound artifact identity, risk score, and rule trace.
      - Never leaks database internal secrets or tokens.
  - POST /api/v1/security-decisions/:id/review (and /security-decisions/:id/review)
    - Role-Guarded Access:
      - API keys: Rejected with HTTP 403 (Human review requires human identity).
      - Auditor JWT: Rejected with HTTP 403 (Auditors are read-only).
      - Analyst / Admin JWT: Allowed.
    - Fail-Closed Business Invariants:
      - Justification minimum length >= 10 characters.
      - Cannot override an ERROR decision or missing required check to ALLOW (HTTP 400).
      - Cannot override confirmed CRITICAL or HIGH threat BLOCKs
        (MALWARE_DETECTED, ARCHIVE_BOMB_DETECTED, ZIP_SLIP_DETECTED, etc.) to ALLOW (HTTP 400).
    - State Transitions & Audit:
      - Inserts new superseding decision row into PostgreSQL `security_decisions`
        with supersedes_id bound to prior decision.
      - Updates `files` status atomically (ALLOW -> 'SCANNED', BLOCK -> 'BLOCKED').
      - Records tamper-evident audit event via `audit_append()`.
      - Returns HTTP 201 Created with newly created decision record.
